Declare Firely's administration operations, and say why the list was empty

Reported as "Run Server Operations says this plugin offers no operations
for firely". Two separate causes, addressed in the order they were
asked for.

**The message.** "This plugin offers no operations for firely" is true
but reads like a fault in the user's setup: the screen works, the list
really is empty, and a user who cannot tell the difference goes looking
for a misconfiguration that is not there. An empty list is the
interface's default, so it means "this plugin has not declared any", and
the message now says that, and says that reading, searching and writing
are unaffected.

It also separates the two reasons a list can be empty, because they
call for different answers. A plugin that declares nothing is a
limitation to know about. A plugin that declared operations this
session cannot run is something to fix by unlocking credentials, and
telling such a user "declares no operations" would send them to the
wrong place.

**The gap.** No shipped plugin overrode availableOperations(); only the
two test fixtures did. The whole machinery around it - ServerOperation,
OperationPathTemplate, PluginOperationClient, the form, the result
classifier, the screen, and 543 lines proving a third-party plugin can
plug in with no core change - had therefore only ever been exercised
against test plugins. The seam was proven and nothing filled it in,
which is why it looked perfect in the suite and empty in the product.

Firely now declares its administration operations: $reindex,
$reindex-all, $preload and $reset, plus a search over each of the
eleven conformance resource types Firely documents.

**The paths were verified against a live Firely Server, not recalled.**
That mattered more than expected, because the branch is
`/administration` and not `/admin` - the plausible guess would have
produced fifteen operations that failed on every real server while
looking entirely correct. The live server also corrected the shape: the
administration API is CRUD on FHIR resources, not bespoke JSON
endpoints, so most of these are searches over conformance resources.
$reindex answered 501 to a GET and $preload 403, which is exactly the
documented "POST-only, network-protected" behaviour. A live
SearchParameter search returned 1457 resources and a correctly shaped
Bundle with the _count and name filters this declares.

**Read-only on the conformance resources, deliberately.** The API does
allow writing them. They are not offered, because changing a
conformance resource changes what a server validates against, and that
should not sit behind a one-click generated form. $reset is listed
because it is real, and described as destructive.

Every operation is marked as requiring credentials, so a locked session
reports why the list is empty - which is the message fix above doing
its job.

The user guide gains the Firely operation list, the empty-list
explanation, and two corrected rows in the known-gaps table.

507 tests, up from 502. Five new ones pin the declared paths, the
conformance type list, the verbs and result kinds, and the read-only
convention - the path assertion exists because that is the one mistake
nothing else would catch.
